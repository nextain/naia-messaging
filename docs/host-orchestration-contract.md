# 호스트 오케스트레이션 계약

이 엔진은 전송·큐 중립이다. 작업 큐·승인·수신자·outbox·워크트리의 정본은 호스트가
쥔다. 아래는 이 엔진을 품는 호스트가 지켜야 하는 계약이고, 엔진 동작 규정이 아니다.
여기 적힌 정책을 엔진 코드로 옮기지 않는다 — 옮기는 순간 모든 호스트가 한 인스턴스의
운영 취향을 상속한다.

증거: onmam-dev Discord 게이트웨이 실운영 회고(2026-09-11). 타이머 자동 재접수가
35시간 동안 78건을 만들어 실행기 크레딧을 소진시키고 스레드를 자동 보고로 덮었으며,
30분짜리 작업이 승인 형식 요구 때문에 4일간 준비 단계에만 머물렀다.

## 엔진이 이미 주는 것

- `core/verdict` — `whoseTurn`·`classifyAgentMessage`. 게시 ≠ 수신 ≠ 시작이고, 수신
  확인은 시작 영수증일 뿐이다. 왜: "받았다"를 응답으로 세면 요청이 조용히 사라진다.
- `core/contact-window` — `shouldContact`. 요청·재촉은 접촉 창 안에서만, 고장 알림은
  언제나. 창 밖 시간은 재촉 횟수에 세지 않는다.
- `core/delivery` — 확인됨 / 실패 / 알 수 없음. `unknown` 은 자동 재전송하지 않고
  저장한 nonce 를 보존한다.
- `engine/discord/backend-runner` + `runtime/backend-task.mjs` — 이미 claim 된 작업
  하나만 1회 실행하고, 실행 증거 원장에 남은 작업의 재실행은 `execution_already_recorded`
  로 거부한다. 턴 상한·타임아웃·종료 사유는 실행 결과에 그대로 실려 나온다.
- `runtime/host-bridge.mjs` `backend` 모드 — 단일 호출, 단일 작업. 큐도 승인도 열지 않는다.

## 호스트가 구현할 것

### 1. claim 순서와 자율 continuation

- **claim 순서는 사람 메시지 → 운영자 접수 → 자동화.** 같은 이슈에 사람 메시지가
  오면 대기 중인 자동 작업은 supersede 한다.
- **자율 continuation 금지.** 타이머로 열린 이슈를 훑어 "이어하기" 작업을 다시 넣지
  않는다. 일을 움직이는 것은 사람 메시지와 명시적 지시뿐이다. 왜: 20분 타이머가
  열린 이슈 전부를 재접수해 35시간 78건과 402(크레딧 소진)를 만들었다.
- 이 루프를 엔진에 넣지 않는다. 엔진은 호스트가 건네준 작업 하나만 실행한다.

### 2. 사람 입력은 강등되지 않는다

- 직전 작업이 실패·타임아웃이었다는 이유로 사람의 후속 메시지를 읽기 전용 "검토"
  작업으로 낮추지 않는다. 실제 효과를 확인하고 남은 일을 계속한다.
- 왜: 사람이 재촉해도 일이 앞으로 가지 않고 검토 보고만 쌓였다.

### 3. 모델 답변은 그대로 전달한다

- 호스트가 모델 답변을 사전 검증 실패로 통째로 버리지 않는다. 적용하는 것은
  redaction(`core/redact`)과 멘션 허용목록뿐이다.
- 왜: 답변 안에 호스트 API 로 검증되지 않은 질문이 하나 있다는 이유로 답변 전체가
  "검증하지 못했습니다"로 대체되어, 실제로 한 일이 사라졌다.

### 4. 끊긴 실행의 제한된 자동 재개

- 턴·시간 상한이나 실행기 취소로 끊긴 실행에 한해, 호스트가 "계속"을 **체인당 최대
  2회** 자동 투입한다. 크레딧 소진·운영자 취소·supersede 는 제외한다.
- 2회를 쓰고 나면 사람이 "계속"이라고 말할 때까지 멈춘다. 무한 재개가 아니다.

### 5. 승인

- 승인을 묻는 범주는 셋뿐이다: (a) 운영 고위험 — 스키마 변경, 대량 삭제, DNS,
  스토리지 철거, 인프라, 시크릿. (b) 운영 고트래픽 조회. (c) 사람만 할 수 있는 결정
  — 유료 라이선스, 실결제 키, 상업 계약. 그 밖은 묻지 않는다.
- **스레드 답글이 승인이다.** 등록 운영자가 스레드에서 실행안에 "승인/진행해"라고
  답하면 그것이 승인이다. 커밋 SHA·정확 명령 문자열·만료·lease·재승인을 요구하지
  않고, 같은 이슈에서 다시 묻지 않는다.
- 확인을 부탁할 때 적는 네 가지(누가·무엇을·정확히 어디서·어디로 보고)는 그대로
  지킨다(`core/confirmation`). 형식 요구와 정보 요구는 다른 것이다.

### 6. 위험 등급과 준비도

- low/medium: 백업 또는 롤백 경로 + 이슈 기록 + 변경 후 검증이면 진행한다.
- high 에만 검토 스크립트·롤백 산출물·독립 위험 검토·배타 lease·공개 스모크를 건다.
- 백업 후 되돌릴 수 있으면 high 가 아니다. high 로 올리면 되돌릴 수 없는 이유를
  이슈에 적는다.
- **준비 부족은 승인 사유가 아니다.** 준비는 봇이 할 일이지 사람에게 물을 일이 아니다.

### 7. 실행 격리와 동시성

- 잡은 **수신 체크아웃 밖의 이슈별 워크트리**에서 실행한다. 브랜치는
  `issue-<n>/<agent>`(기존 이슈 브랜치가 있으면 재사용), 기준은 통합 브랜치.
- 워커는 수신 체크아웃과 본 클론을 바꾸지 않는다. 왜: 워커의 `git checkout` 이 수신
  프로세스의 HEAD 를 바꿔 수신이 깨진 적이 있다.
- 닫힌 이슈의 워크트리는 정리하되 dirty 면 보존한다.
- 슬롯은 1보다 크게 둔다(실증 2). **같은 이슈·같은 스레드는 동시에 1건**이고, 배포·
  공유 DB·운영 변경은 잠금으로 직렬화한다.

### 8. 워커 상한

- 턴·시간 상한은 실제 작업이 끝날 수 있는 값으로 잡는다(실증 150턴 / 3600초). 값은
  환경 변수로 조정한다. 왜: 40턴/25분이 실제 배포를 중간에 끊었다.
- 상한에 걸린 실행은 "불확실"이 아니라 **"중단"**이다. 중단을 불확실로 읽으면 작업이
  준비 단계로 되돌아간다.

### 9. 헤드리스 백엔드

- 권한 프롬프트가 열리지 않는 모드로 실행한다. deny 규칙은 그대로 유지한다.
- 백그라운드 작업이 끝나기 전에 턴을 끝내지 않는다.
- 마지막 메시지는 `[역할]` 로 시작하는 최종 보고 하나다.
- **`stopReason` 이 `end_turn` 이 아니면 완료가 아니라 중단이다.** 종료코드 0 과 중간
  서술만으로 완료를 기록하지 않는다. 왜: 헤드리스 실행기가 권한 프롬프트를 열고
  30초 뒤 취소된 실행이 "완료"로 전달된 적이 있다.
- 하지 않은 일을 완료로 쓰지 않는다.

### 10. 알림 범위

- 소유자 DM 은 게이트웨이 사망, 토큰 충돌, 기한 있는 소유자 승인 — 이 셋만.
- 나머지는 전부 스레드로 보낸다. 소유자는 기본 수신함이 아니다.

## 설정이 사는 곳

`maxConcurrentJobs`(7), `backend.maxTurns`·`backend.timeoutSeconds`(8)는 호스트 설정
이며 `runtime/config-schema.mjs` 의 스키마에 없다. 이 저장소의 설정은 전송·바인딩·
접촉 창의 *형태*만 검증한다.
